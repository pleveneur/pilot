# Spécifications — Pilot

> Spécifications fonctionnelles et techniques de l'éditeur Pilot.
> Architecture, stack et arborescence : `AGENTS.md`.
> Chaque feature a sa spec dédiée (table de navigation rapide dans `AGENTS.md`).

**Pilot** est un **environnement de développement intégré (IDE)** multiplateforme (Tauri v2, Rust + HTML/CSS/JS/Vite) dont le cœur est constitué des agents IA de codage **pi** et **plh**. Les **fournisseurs et modèles LLM sont paramétrables** (certains modèles peuvent ne pas être testés). Pilot porte la **vision particulière de son développeur (Patrick Leveneur)** avec une **intégration maximale de l'IA** : un **assistant de codage** mais aussi un **assistant de suivi de dossiers** — suivre une activité efficacement et faire des propositions et ajustements élaborés.

## 1. Interface

**Boutons de fenêtre** (`#window-controls`, groupe fixe haut-droite, au bout de la rangée d'onglets) : la barre de titre système est retirée sous Windows et Linux (`set_decorations(false)` dans `setup`, macOS garde son cadre) et **il n'y a plus de bande haute** (les 32 px de `#window-bar` sont supprimés) : **Réduire / Agrandir-Restaurer / Fermer** (`close()`, jamais `destroy()` : la confirmation et le keep-alive restent maîtres) sont le **dernier enfant de `#tab-row`**, place réservée dans le flux (`flex: 0 0 auto` : aucun onglet ne passe dessous), et restent **au-dessus** du chargement, des dialogues d'agent et du mode immersif (`z-index: 100001`), avec 4 px d'air (`padding: 4px 4px 4px 0`) donc des touches de **46 × 28 px**. Le **déplacement de la fenêtre** (glisser + double-clic = agrandir/restaurer) se fait sur les surfaces non cliquées : **bandeau du nom de projet** et **vide de la rangée d'onglets** (garde-fou unique `WINDOW_GESTURE_BLOCKLIST` : boutons, onglets, champs, menus, entrée « Travail », boutons de fenêtre en sont exclus). Permissions : `core:window:allow-minimize`, `allow-toggle-maximize`, `allow-close`, `allow-start-dragging`, `allow-set-position`, `allow-set-size`. **Clic droit** sur Agrandir = menu « Disposer » à trois entrées (moitié gauche / moitié droite de l'écran, plein écran — `src/js/window-controls.js`) ; le clic gauche garde son effet. Voir `docs/proposition-barre-fenetre.md`.

Trois zones : **Barre Latérale** (gauche), **Zone de Travail** (droite), **Panneau d'Actions** (bas gauche). Nom donné au système (barre des tâches, Alt+Tab) : toujours `Pilot`, jamais le chemin du projet.

### Trois modes d'écran (Détaillé · Assistant seul · Vocal)
- **Le bouton unique est le LOGO Pilot** (`#mode-logo`, dans le bandeau du nom de projet, autour de l'image `#btn-project-logo`) : un clic fait le tour Détaillé → Assistant seul → Vocal ; l'infobulle dit le mode courant et annonce le suivant ; **ni mot, ni pastille** (le logo est muet). **Garde de 400 ms** : un double-clic réflexe ne change qu'un seul mode. Dans les **deux pleins écrans** le logo est **déplacé** dans l'overlay et y prend **la même place** que dans « Détaillé » (une seule règle CSS, 13 px / 8 px) ; à la sortie il revient **exactement** à sa place (parent + voisin mémorisés). Voir `CONCEPTION-logo-bouton-des-trois-modes.md`.
- **Comment changer de mode** : le **logo** (cycle complet), **`Ctrl+Shift+A`** (entrer ou sortir d'un plein écran, depuis n'importe où), **`Échap`** (sortir du mode Vocal) et la **fermeture de l'onglet 🧭** (retour à Détaillé). Aucun autre chemin, aucun écran de réglage.
- **Mémorisé** dans une seule clé (`pilot_screen_mode`), ancien réglage binaire repris une fois ; un mode plein écran mémorisé rouvre l'onglet 🧭 au lancement. Aucun écran de réglage.
- **Mode Vocal** : objet lumineux, trait de niveau réel, **une** ligne d'état, saisie déplacée, micro de mesure ouvert **en premier** dès l'entrée (la dictée vient après) et **rendu** à la sortie, parole par-dessus Pilot = lecture arrêtée → [`spec_modes_ecran_vocal.md`](spec_modes_ecran_vocal.md).
- **Mode Zen** (`F11`, plein écran sans barre latérale) : la colonne de gauche disparaît, donc le logo aussi ; les trois modes restent atteignables par `Ctrl+Shift+A` — **aucun mécanisme ajouté** pour le Zen (décision D7 = A).

### A. Barre Latérale
- **Sélecteur de projet** : bouton "Projets" (📁 Nouveau + 10 récents). Un dossier = un "Projet de l'Agent IA".
- **Arborescence** : tree view sans racine, flèches ▶/▼, temps réel (poller custom), drag & drop externe, expansion persistée, **badges Git** (`M`/`A`/`D`/`?`, dossiers contenant une modification marqués `•`) + diff visuel read-only (CLI `git`, zéro dépendance Cargo). Les dossiers lourds/non pertinents (`node_modules`, `.git`, `target`, `dist`, `build`, `vendor`, environnements virtuels Python, caches IDE/CI…) sont ignorés à la lecture **et** par le watcher (liste unique `IGNORED_DIRS`, `lib.rs`) pour éviter l'explosion mémoire sur les gros projets.
- **Filtre** : champ texte, `Ctrl+P`. **Favoris** : section « ⭐ Favoris » collapsible, clic droit (ajouter/retirer), `Ctrl+Shift+B` pour le fichier actif, persistés en config.
- **Menu contextuel** : `.md` → prévisualiser / exporter PDF / supprimer / envoyer à l'agent Pi ; `.pdf` → prévisualiser / **créer un fichier Markdown** (heuristiques + IA configurable) / supprimer ; `.csv` → prévisualiser ; autre fichier → envoyer à l'agent Pi / supprimer ; dossier → créer fichier/dossier, supprimer, analyser ; zone vide → créer. Suppression avec confirmation native (onglets concernés fermés automatiquement) ; menus natifs WebView2 désactivés (issue #23) au profit d'un menu custom Copier/Couper/Coller dans l'éditeur et les champs.

### B. Zone de Travail
- **Rangée d'onglets** (`#tab-row`, 36 px, dans le flux, **tout en haut de la fenêtre**) : la **barre d'onglets** (`#tab-bar`, largeur restante, défilement horizontal), l'entrée **« Travail »** (`#agent-activity`, place réservée qui ne défile pas) et, **au bout à droite**, les **trois boutons de fenêtre**. La **bande de contexte de 26 px** est supprimée (le projet se lit à gauche, l'onglet actif se signale par son fond et son filet). L'entrée reste **dans la zone de travail** et hors de `#tab-bar` (dont les enfants sont « onglets + bouton d'ajout d'agent » pour `tabs.js`). Voir `docs/proposition-bande-contexte-allegee.md`.
- **Édition et prévisualisations** : CodeMirror 6 multi-langages (14 langages, chargement lazy + folding ; blocs de code Markdown colorés) — `.md`, `.js`, `.ts`, `.py`, `.rs`, `.json`, `.yaml`, `.html`, `.css`, `.sql`, `.java`, `.cpp`, `.xml`, `.php`… ; prévisualisations **Markdown** (markdown-it + Mermaid + KaTeX `$...$`/`$$...$$`, liens internes/externes/ancres) avec **split** éditeur+aperçu (`Ctrl+Shift+E`, scroll synchronisé dans les deux sens), **PDF** (PDF.js), **images** (zoom/fit), **CSV** (tableau HTML).
- **Terminal intégré** : xterm.js + PTY. **Agent Pi** : RPC → [`spec_rpc.md`](spec_rpc.md). **Multi-onglets agents** : onglets π indépendants, configurés par projet dans `.pilot/agents.json` → [`spec_project_agents.md`](spec_project_agents.md). **Agents multi-rôles** (coordinateur + agents spécialisés, protocole `[[CALL:…]]` séquentiel) → [`spec_gestion_agents.md`](spec_gestion_agents.md) ; **Prompt Builder** : clic droit → ajouter + templates + envoi à l'agent Pi.
- **Raccourcis** : `Ctrl+B`/`Ctrl+I`/`Ctrl+K` (Markdown), `Ctrl+Shift+E` (split), `Ctrl+Shift+F` (recherche globale full-text, regex + filtre par extension), `Ctrl+Shift+O` (outline), `Ctrl+Shift+P` (palette de commandes fuzzy), `Ctrl+G` (aller à la ligne), `Ctrl+Tab`/`Ctrl+Shift+Tab` et `Ctrl+1…9` (onglets), `Ctrl+Shift+S` (enregistrer sous), `Ctrl+Space` (complétion IA inline : ghost text, `Tab` accepte, `Échap` rejette), `F11` (mode Zen).
- **Barre de statut** : mots / caractères / lignes + temps de lecture (~200 mots/min), encodage (UTF-8 / BOM / UTF-16), fin de ligne (LF/CRLF), indicateur d'auto-save configurable (défaut 3 s, sauvegarde tous les onglets dirty). **Divers** : images (drag & drop / `Ctrl+V` → copie dans `images/` + `![]()`), export PDF (HTML + `window.print()`, KaTeX inclus), notifications toast non bloquantes, sidebar redimensionnable (largeur persistée, double-clic = 280 px), onglets (sauvegarde auto, conflit → flash rouge, fermeture auto au changement de projet, confirmation avant de fermer l'onglet Agent).

### C. Panneau d'Actions
- ⚙️ **Paramètres** : **onglet** des Réglages (et non plus une fenêtre — bascule du lot B de `docs/proposition-reglages-en-onglet.md`) : le nœud `#settings-modal` est **déplacé tel quel** dans le conteneur d'onglet (classe `.modal-in-tab`, qui ne neutralise que le positionnement). Ouverture par le bouton ⚙, la palette ou un événement externe : **un seul chemin** (`_openSettings`), un onglet déjà ouvert n'est ni recréé ni rechargé (`switchTab`). Le **✕ de l'onglet vaut « Annuler »** (chemin normal de fermeture, sans confirmation, retour à zéro : aperçu de thème annulé, sondes Laya arrêtées, lecture à voix haute arrêtée) ; « Annuler » et « Enregistrer » gardent leur effet mais **ne ferment plus l'onglet**. Ouvrir les Réglages **quitte d'abord le mode « Assistant seul »** ; l'onglet est **transverse** (il survit aux bascules et fermetures de projet). Onglets verticaux (Général / Agent Pi / Modèles IA / Accès distant / Avatar / Serveurs MCP + écrans transverses GDS et service Laya). Thème dark/light + sous-thèmes (5 par mode, aperçu en direct), commande défaut, auto-load projet, terminal (intégré/externe), params RPC, word wrap, niveaux de réflexion (défaut global, par agent, Assistant — voir [`spec_rpc.md`](spec_rpc.md) § 4ter).
- **Bas de la colonne (cadre accent, le seul de l'interface)** : **SEPT lignes** de 32 px, toutes de la même taille (**plus aucune ligne mise en évidence**) — **Brouillon** (`btn-scratchpad`) et **Options** (`btn-settings`) en tête (elles ont quitté le haut de la colonne, mêmes libellés/infobulles/icônes/identifiants ; voir `RAPPORT-design-colonne-entrees.md` § 2.2) — puis **Assistant**, **Dossier du projet** (`btn-explorer` : ouvre le dossier du projet dans l'explorateur du système), **Terminal**, **Commandes du projet** (`btn-commands`), **Outils ▾** (libellé **affiché** de la ligne, au pluriel ; le menu qu'elle ouvre s'appelle **« Autres outils »** : menu ouvert **vers le haut**, **10 entrées** groupées, **« Lancer l'agent » en PREMIÈRE ligne** du groupe « Mon projet » : Prompt Builder / Tableau de bord, Graphe du projet, Historique des sessions / Revue de code / Équipe d'agents, Kanban, Discussion inter-projets / GDS du projet ; **tant que ce menu est ouvert la ligne « Outils » elle-même ne se voit plus** — classe `open` posée par `sidebar.js`, règle `#btn-more-screens.open` de `style.css` en `opacity: 0` + `pointer-events: none`, **jamais** `display`/`visibility` : la place de 32 px reste réservée, donc **aucun saut** du panneau ni du menu, et le bouton reste focalisable — elle revient telle quelle à la fermeture, cf. `docs/rapports/RAPPORT-bouton-outils.md`). Le cadre reste affiché **sans projet ouvert** (il ne montre alors que Brouillon et Options) : il n'est plus `project-only hidden`. Hauteur **278 px** (2 + 16 + 7 × 32 + 6 × 6) ; **plafond 60 % de la hauteur de fenêtre** = 300 px à la fenêtre minimale (500 px) : marge de 22 px, **aucune ligne hors cadre** (`overflow: visible` reste obligatoire pour le menu qui s'ouvre vers le haut, donc un débordement ne serait pas rattrapé par un défilement). Voir `docs/proposition-presentation-ui.md` § 3.3. **Repli au survol (LOT 1)** : au repos le bloc est **replié** (cadre de **50 px**, seule la **dernière ligne** reste visible, mêmes libellé/icône/identifiant ; son **infobulle** est **enrichie** et **nomme les six autres lignes** — décision Q2 du propriétaire, aucun libellé nouveau) ; le survol le déploie après **100 ms**, le clavier immédiatement et sans animation ; il se replie après **300 ms** de sursis (+ 180 ms d'animation) quand ni la souris, ni le focus, ni le menu ouvert ne le retiennent. L'ancre est le bas du cadre : la ligne du bas ne bouge jamais, la colonne reste à 280 px, aucun nœud, bouton ni réglage ajouté (`src/js/sidebar-footer-fold.js`, verrou `src/js/repli-menus-bas.test.js`). **LOTS 2 à 4** : le **parcours clavier complet** est verrouillé (entrer, atteindre la ligne d'ancrage, ouvrir le menu, **circuler dedans**, en sortir ; le repli ne se déclenche **jamais** tant que le focus ou le menu tiennent, et `Échap` ne double jamais le menu — le menu vit **dans** le cadre) ; au **doigt**, le **premier appui déploie sans rien déclencher** (appui consommé, décision Q1) — le **doigt ne survole pas** : les deux évènements de survol d'un pointeur tactile sont ignorés, donc le bloc **ouvert au doigt reste ouvert** (le doigt levé ne le referme jamais, sinon le second appui retomberait sur un bloc replié) — et un appui **hors** du bloc déplié le replie tout de suite ; en **mouvement réduit** (réduction système **et** réglage « Animer l'ouverture des modales » désactivé) la classe `no-motion` retire l'animation (`#project-footer.no-motion { transition: none }`) en **conservant les délais** de 100 ms et 300 ms (décision Q3 : ce sont des absorbeurs de gestes, pas du mouvement). Voir `RAPPORT-conception-repli-menus-bas.md`, `RAPPORT-repli-menus-bas-lots2-4.md` et `RAPPORT-repli-menus-bas-toucher.md`.
- **Colonne : haut, bas, bandeau.** Plus **aucun bouton en haut** : `#global-actions` reste dans le DOM mais **vide** (aucune hauteur réservée) ; le badge « Distant » est **descendu** dans la **ligne du bas** (`#sidebar-engine-row`, 28 px, sous le cadre accentué) où il est **seul, aligné à droite** — la ligne garde donc 28 px, l'arrivée d'un client distant ne fait pas sauter la liste des fichiers. Le **bandeau** (48 px, logo 24 px, nom du projet 15 px) porte **le sous-titre du moteur en service** (`#project-engine` : « Moteur · Agent Pi » / « Moteur · Agent PLh », source unique `src/js/backend-info.js` via `main.js`, rafraîchi à chaque re-sonde) : c'est **le seul endroit de l'interface de travail qui nomme le moteur**. Voir `RAPPORT-nom-du-moteur-un-seul-endroit.md`.
- **Barre de statut** : celle des **fichiers** (type, curseur, encodage, fin de ligne, auto-save) ; dans un onglet de chat (π, 🧭) elle est **vidée** (un seul endroit nomme le moteur : le bandeau). **Autres accès** : **Agents** · **Review** · écrans GDS (« GDS Serveur », « GDS paramétrage ») · **Coffre** · **Feedback** (accessible sans projet).

### D. Design system & icônes
- **Design tokens CSS** partagés (`--space-*`, `--radius-*`, `--shadow-*`, `--ring`, `--transition*`) + ombres / anneau de focus par thème, utilisés par tous les composants (modales, boutons, inputs, onglets, menu contextuel). **Panneaux translucides (verre)** : leur teinte a **une seule source**, les jetons `--glass-tint` (surface d'un panneau flottant, 94 %) / `--glass-scrim` (voile de fenêtre) / `--glass-scrim-soft` (voile d'attente) et `--glass-frame` (cadre d'un panneau :
`color-mix(in srgb, var(--text-secondary) 80%, transparent)`, même famille que le texte
qu'il entoure — **5,32:1** en sombre, **3,69:1** en clair, jamais plus contrasté que le
texte ; arrondi par `--radius-lg`), déclarés dans `.theme-dark` et `.theme-light` **à partir** des variables du thème (jamais une couleur recopiée, aucun sous-thème ne les fige) : la teinte suit donc les dix palettes et se recalcule à chaque changement de thème. Les surfaces qui floutent l'arrière-plan sont rafraîchies au changement de thème (`src/js/glass-theme.js`, classe `body.glass-refresh` posée une image, écoute de l'évènement `THEME_CHANGED_EVENT` de `theme.js` — **aucun réglage, aucun stockage**) : sans cela le compositeur gardait l'instantané de l'ancien thème jusqu'au redémarrage. Verrous : `src/js/panneaux-translucides-theme.test.js` (teinte) et
`src/js/cadre-listes-panneaux.test.js` (cadre : couleur, arrondi, mesure, contraste). **Icônes Lucide** (SVG inline ; `src/js/icons.js` : `refreshIcons`, `setIcon`, `setIconText`) à la place des emojis, tailles `.icon`/`.icon-sm`/`.icon-lg`, couleur `currentColor`, icône par type de fichier (`FILE_ICONS` / `FILE_NAMES`) et coloration par catégorie (`ICON_CATEGORY` → `icon-cat-*`).

## 2. Spécifications Techniques

- **Persistance et mode dev** : config JSON dans `app_data_dir` (thème, commande, projets récents, params RPC, options) ; permissions Tauri `core:default` + `dialog:default` + `updater:default` + `process:default`. `npm run tauri dev` (wrapper `scripts/tauri.js` + `tauri.dev.conf.json`) prend l'identifiant `com.pilot.editor.dev` et un port web décalé de +1 → la version dev tourne en parallèle de l'installée (single-instance et `app_data_dir` distincts, issue #25).- **File watching** : poller custom (`read_dir` récursif filtré par `IGNORED_DIRS`, 2 s) → événements `file-change`, debounce 500 ms + déduplication. Remplace `notify::PollWatcher` (re-scan complet qui figeait l'UI sur les gros projets Rust).
- **PTY (terminal intégré)** : `portable-pty` (ConPTY Windows, PTY natif macOS/Linux), shell `cmd.exe` / `$SHELL` (zsh/bash) ; sous Windows le PATH complet (registry HKLM + HKCU) est injecté dans le PTY. Streaming `terminal-output`, `Ctrl+C` = copie si sélection sinon SIGINT.
- **Aucun lancement ne fait clignoter de fenêtre de console** : Pilot est une application GUI ; tout processus console lancé sans masque ouvrirait une fenêtre noire. Le masque a **un seul point** : `hide_console(&mut cmd)` dans `gds-core/src/proc.rs` (drapeau `CREATE_NO_WINDOW` défini **une seule fois**, fonction neutre hors Windows), réexporté par `lib.rs` (`crate::hide_console`) — le masquage est transitif, donc une ligne par lancement suffit (y compris le `cmd.exe` intermédiaire du terminal, dont la fenêtre finale reste ouverte par `start`). Un lancement **volontairement visible** porte une marque motivée `FENETRE-CONSOLE-EXCEPTION : …`, jamais une exception silencieuse. Garde automatique : `src/js/fenetres-noires-lancements.test.js` (tout `Command::new` des sources Rust doit être masqué ou marqué, aucun littéral de drapeau hors du point unique) → [`docs/rapports/RAPPORT-fenetres-noires-correction.md`](docs/rapports/RAPPORT-fenetres-noires-correction.md).

### Agent Pi (RPC)
- Processus `pi --mode rpc` (ou programme 100 % compatible pi, ex. plh) piloté en JSON/JSONL ; sessions gérées par l'`AgentService` (clé composite (projet, agent), parking, pointeur actif). Détail complet : [`spec_rpc.md`](spec_rpc.md).
- **Démarrage auto** : `agent_start_on_launch` (défaut **false**) règle **tout** démarrage automatique de l'agent (au lancement de Pilot et à l'ouverture/bascule d'un projet) ; `super_agent_start_on_launch` (défaut **true**) rouvre l'onglet 🧭 Assistant → [`spec_multiprojects.md`](spec_multiprojects.md), [`spec_super_agent.md`](spec_super_agent.md).
- **L'agent lancé est exactement l'agent demandé (mission 381)** : `run_agents` / `run_assistant_agents` démarrent **directement** les agents nommés — **aucune estimation préalable** (« devis ») n'est déclenchée, le texte de la mission n'est **jamais** remis à un agent non demandé, et aucun accusé « en préparation » n'est plus produit. Un identifiant **inconnu** est **refusé** (identifiants inconnus + liste des agents disponibles, aucun agent lancé) ; un agent demandé mais **impossible à démarrer** produit une erreur qui le **nomme** — jamais de routage silencieux vers un autre agent, ni côté frontend (`super-agent.js`, `agents-bus.js` : `dispatchParallel` lit l'agent par son identifiant exact) ni côté Rust (`AgentService::start` ne substitue jamais l'agent : au besoin il crée la ligne du **même** identifiant). Détail : [`spec_super_agent.md`](spec_super_agent.md) § outils d'agents ; tests `agent-demande-exact.test.js`, `agent-inconnu-refus.test.js` (preuve d'exécution : rien ne démarre), `verrou-par-projet.test.js` (T6).
- **Santé et mise à jour du backend** : health check `--version` au lancement → gate « π indisponible » dans l'onglet agent, re-sonde au changement de chemin pi (E4) ; si backend `pi` et `pi_skip_update_check` false, comparaison avec la dernière version → modale [Mettre à jour] (`pi update --self`) / [Plus tard] / [Ne plus demander] (issue #26). **Règle de démarrage** : la vérification de la version de `pi` est la **toute première** chose faite au lancement, et pendant elle (comme pendant une installation de `pi`) **rien ne démarre** — commande manuelle, lancement par l'Assistant, mission (même en file), rejeu, délégation : un seul gardien (`run-policy.js`) consulte l'état détenu par `pi-startup-gate.js`. La séquence est **bornée** et rend toujours le terrain : en cas d'échec ou de lenteur, l'utilisateur est informé (`pi update --self`) et le travail reprend (jamais de blocage définitif). Détail : [`spec_rpc.md`](spec_rpc.md) §4bis.
- **Extensions pi embarquées** : Mode Orchestration → [`spec_orchestration.md`](spec_orchestration.md) ; quality-gate 🛡️ (protocole anti-régression, persistant, relance l'agent) → [`spec_quality_gate.md`](spec_quality_gate.md) ; porte pré-écriture (diff avant/après des `write`/`edit`) → [`spec_diff_review.md`](spec_diff_review.md) ; boutons de choix/confirmation/saisie → [`spec_rpc.md`](spec_rpc.md) §8bis ; MCP (voir ci-dessous).
- **Avatar (PLface)** : Paramètres → Avatar — `plface_autostart_enabled` (défaut false), `plface_exe_path`, `plface_avatar_path` ; programme et modèle livrés avec Pilot (`assets/plface.exe`, `assets/PilotBase.vrm`, résolus dynamiquement, sinon aucun lancement en silence). Pilot sonde l'API locale du visage et le lance détaché si elle ne répond pas ; un avatar lancé par Pilot est **tracé** (`plface.pid`, avec son **propriétaire** : identifiant + nom du programme de Pilot) et refermé **par la seule copie qui l'a lancé** (arrêt propre `GET /close`, garde sur le nom du processus) — jamais celui d'une autre copie encore ouverte ni un avatar lancé à la main ; même règle de propriété que le service Laya (une seule définition des décisions d'arrêt). Lancement toujours `--no-taskbar`. Boutons « Tester maintenant » / « Arrêter mon avatar ». Fail-open, non bloquant (`plface.rs`, `plface-utils.js`). Doc utilisateur : `help/overview.md`.

### Features transverses (une spec dédiée par sujet)

le **dernier contrôle** (date + verdict) est conservé et lisible en langage clair (palette « État des mises à jour »), « à jour » et « échec » n'étant jamais confondus. **Report et installation (P5)** : « Plus tard » / ✕ est **mémorisé** pour la version concernée — elle n'est **plus reproposée** jusqu'au prochain démarrage (une version **différente** l'est toujours) ; les contrôles déclenchés par un **retour au premier plan** sont espacés d'au moins **5 min** (`FOREGROUND_MIN_INTERVAL_MS`) ; **une seule installation à la fois** (`_installing`) : un contrôle de fond pendant l'installation ne réactive ni le bouton ni la progression, et un second clic affiche un message au lieu de lancer une seconde installation ; la commande manuelle **répond** aussi quand un contrôle est déjà en cours. **Mise à jour NON BLOQUANTE et réversible (règle propriétaire, 2026-11)** : l'écran de mise à jour ne s'affiche **que si aucun agent ne travaille** (règle revérifiée **au moment d'afficher**, jamais d'écran fantôme) ; sinon la mise à jour est **mémorisée** et s'affiche **d'elle-même** à la libération du terrain (toast discret + rappel `#status-update-waiting`, travail jamais interrompu). **L'écran simplement OUVERT ne réserve plus le terrain** : envoyer, laisser l'assistant répondre, les missions et la file continuent — **seule une INSTALLATION réserve** (pendant elle, aucun agent ne démarre et les demandes en file **restent en file**). L'écran reste **rouvrable à la demande** (palette « Vérifier les mises à jour », ou clic sur le rappel de statut) **même après « Plus tard »** ; le report n'**efface plus** le rappel, qui devient « disponible — non installée ». Aucune priorité n'est plus accordée à l'attente (l'ancienne règle d'attente, retirée, retardait les relances automatiques). Ce rappel **nomme** désormais l'agent et le projet qui **bloquent**, avec l'**ancienneté** du travail (« codeur (Pilot) en cours depuis 2 h 13 min » ; plusieurs sessions ⇒ la plus **ancienne** est nommée puis « + N autres ») : texte produit par la fonction **pure** `formatWaitingNotice()` à partir de la sonde `setUpdateWorkHoldersProbe` posée dans `main.js`, qui lit le relevé d'activité **déjà en mémoire** (aucune requête, aucun sondage supplémentaire) ; sonde absente, vide ou en échec ⇒ texte historique **mot pour mot** (aucun nom, aucune durée inventés). État et textes de refus : **une seule source**, `src/js/update-window.js` (`reserveUpdateWindow` / `isUpdateWindowReserved`), consultée par le gardien **existant** `run-policy.js` (`canStartWork` → `canSendManualCommand*`, `workBlockedMessage`) — **pas de second gardien**. Artefacts signés (clé publique dans `tauri.conf.json`, clé privée en secret GitHub `TAURI_SIGNING_PRIVATE_KEY`), workflow `.github/workflows/release.yml` (tag `v*` : release idempotente → builds Windows NSIS/MSI, macOS DMG x86_64/aarch64, Linux AppImage → `latest.json` généré par `scripts/gen-latest-json.js`), changelog utilisateur `release-notes/vX.Y.Z.md` (fallback catégorisé depuis `git log`). **Paquet proposé = type d'installation réel** : pour `windows-x86_64`, seul le NSIS `…-setup.exe` est retenu (installation `installMode: currentUser`) ; le MSI est **écarté explicitement** et ne peut plus écraser l'entrée (logique pure `scripts/latest-json-platforms.js`).

### Mode consommateur MCP
- **Deux transports** : **local** (`stdio`) et **distant** (`http`/`https`) via une extension pi qui embarque le SDK MCP (source `mcp-client.src.ts` → `npm run build:mcp` → `pilot-mcp-client.ts`, **généré, jamais édité à la main**). Config `mcp.json` (dans `app_data_dir`, pas dans AppConfig) : `McpServer { id, name, transport, enabled, command, args, url, secret_ref }` ; l'extension découvre `tools/list` et enregistre chaque outil en `mcp_<serverId>_<name>` (fail-open), serveur cible `PILOT_MCP_SERVER` sinon le 1er serveur activé. Un échec d'outil MCP remonte à l'agent comme **erreur** (`isError` transmis tel quel) : un refus du serveur n'est jamais présenté comme une réussite.
- **Nom des outils (règle réelle, vérifiée)** : un **seul serveur MCP est chargé par session** (cible activée, sinon le premier activé — mêmes règles que `select_session_server`) : deux serveurs ne peuvent donc **pas** se disputer un nom d'outil dans une même session, et le format `mcp_<id>_<outil>` (**inchangé**) ne bouge pas pour les configs qui fonctionnent. Le cas ambigu est rendu **explicite**, jamais silencieux : (a) deux entrées de `mcp.json` portant le **même identifiant** produiraient exactement les mêmes noms d'outils ⇒ **chargement refusé** avec un message qui nomme les deux serveurs (le second était auparavant ignoré sans un mot) ; (b) un outil déclaré **deux fois** par un serveur ⇒ seule la **première** déclaration est exposée, le doublon est signalé (pi range ses outils par nom : l'ancien comportement écrasait en silence). Règle et détection dans **une seule source**, `src/js/mcp-tool-names.js` (pure, bundlée dans l'extension, testée par `mcp-tool-names.test.js`).
- **Sécurité** : la clé d'accès n'est **jamais** dans `mcp.json`, seulement la **référence** de l'entrée du coffre (`secret_ref`, forme `vault:<id>`, le préfixe étant facultatif) ; la valeur est résolue côté Rust (coffre déverrouillé) et transmise en **en-tête** `Authorization` (`PILOT_MCP_SECRET`) pour un serveur distant, dans l'**environnement** du programme pour un serveur local, masquée dans les erreurs et jamais renvoyée à l'UI. La référence est un identifiant technique : elle se choisit dans la **liste déroulante des entrées du coffre** du champ « Clé demandée » (ou se saisit à la main), est **affichée dans l'onglet 🔐** (cliquer pour copier), et est lue par `vault_list_refs` (jamais les mots de passe). **Périmètre de la clé (tâche 399)** : la clé n'est transmise **qu'au serveur qui la déclare lui-même** (« Clé demandée » de sa fiche, local comme distant) — un serveur qui ne demande rien ne la reçoit jamais, même par héritage de l'environnement de l'agent (`mcp_secret_strict`, **strict par défaut**, logique pure `src/js/mcp-secret-scope.js` partagée avec l'extension). Référence introuvable → **lancement de ce seul serveur refusé**, en la nommant ; coffre verrouillé ou référence vide au lancement de l'agent → le serveur démarre **sans clé** avec un message lisible (et le test de connexion affiche l'état de la clé). Désactiver le mode strict restaure l'ancien comportement.
- **Chargement et confirmation (briques B et C)** : super-agent au spawn si `mcp_enabled` (brique A) ; agents d'assistant/multi-rôles **à la demande** uniquement, via `mcp_server` passé à `run_agents`/`run_assistant_agents` → assignments → `start_agent_process` / `start_assistant_agent_process`. `mcp_agent_confirm` (défaut **ON**) : l'assistant lit l'état via `mcp_state` et, si ON, demande `ask_confirm` avant qu'un agent utilise un serveur. Limite connue : les variables d'environnement ne valent qu'au spawn (une session reprise ne change pas de serveur).
- **Activer / désactiver un serveur depuis la conversation** : l'Assistant le fait lui-même (`mcp_enable_server` / `mcp_disable_server`, sentinel `PILOT_ASSISTANT_MCP_SERVER::`, décision pure `src/js/mcp-server-toggle.js`, écriture `mcp_set_servers_enabled`) — plus besoin de passer par les Paramètres. **Activation exclusive** : un seul serveur branché par session, donc activer coupe les autres et le **dit** ; désactiver n'active personne. L'écriture ne change **que** le champ `enabled` (aucun serveur créé/supprimé, aucun contenu ni secret touché, `mcp_enabled` / `mcp_agent_confirm` / `mcp_secret_strict` inchangés) ; identifiant inconnu → message clair, rien n'est écrit. Effet à la **prochaine session d'agent**. Confirmation demandée par l'Assistant (`ask_confirm`), pas par l'outil. Voir `spec_super_agent.md` § MCP piloté par l'Assistant.
- **UI, commandes et contrôle de l'écran** : Paramètres → « Serveurs MCP » (activer MCP, case de confirmation, **case « Restreindre la clé du coffre au serveur qui la demande »** = `mcp_secret_strict`, lister/ajouter/modifier/supprimer, « Tester la connexion » ; éditeur unique avec bascule *Local (commande)* / *Distant (adresse)* et champ « Clé demandée » **commun aux deux types**) ; commandes `mcp_list_servers`, `mcp_save_servers`, `mcp_test_connection`, `mcp_set_enabled`, `mcp_set_agent_confirm`, `mcp_set_screen_guard`, `mcp_get_state`, `mcp_set_servers_enabled` ; helpers purs `src/js/mcp-utils.js`, `src/js/mcp-secret-scope.js`, `src/js/mcp-tool-names.js` et `src/js/mcp-server-toggle.js`. **Serveurs « écran »** (`screen` dans `mcp.json`, sinon détection par nom/commande) : autorisation **activée par défaut en mode simulation** (`screen_control_enabled` / `screen_control_simulation` / `screen_control_emergency_stop` dans AppConfig, relus **en direct à chaque action** → effet sans redémarrage) ; **chaque action** passe par une confirmation utilisateur (dialogue dédié, sentinel `PILOT_SCREEN_GATE::` ; refus automatique en orchestration autonome ou sans UI) ; mode simulation = tout est tracé mais **rien n'est exécuté** ; **journal** lisible par projet (`.pilot/screen-actions.log` : heure, outil, accepté/refusé/simulé, détails **masqués**) ; **arrêt d'urgence** persistant (bouton 👁 ou dans le dialogue) qui coupe l'autorisation **et** refuse l'action en attente. Logique pure `src/js/screen-guard.js` (portée par l'extension MCP bundlée).

## Commandes du projet (▶)

Lancez vos commandes de compilation / tests / etc. depuis la ligne
**« Commandes du projet »** du bas de la colonne de gauche (icône **▶
square-terminal**).

- **Ouvrir** : cliquez sur l'icône ▶ → la liste des commandes du **projet courant**
  s'affiche (vide au début).
- **Ajouter** : bouton **Ajouter**, renseignez un **nom**, la **commande** (ex:
  `npm run build`) et éventuellement un **dossier de travail** relatif au projet
  (ex: `web/`). Laissez vide pour partir de la racine du projet.
- **Modifier / Supprimer** : boutons ✏️ / 🗑 sur chaque ligne (la suppression est
  confirmée).
- **Lancer** : cliquez sur une commande → elle se lance dans le dossier configuré dans un **onglet terminal** (titre = nom de la commande), et la **sortie (temps réel)** s'affiche dans cet onglet. La liste des commandes se ferme. Vous pouvez continuer à travailler pendant l'exécution.
- **Relancer** : cliquez à nouveau sur la même commande → Pilot **bascule sur l'onglet déjà ouvert** (sans relancer le process).
- **Fermer** : fermez l'onglet pour **arrêter la commande** (comme un terminal intégré).
- Les commandes sont **propres à chaque projet** (fichier `.pilot/commands.json`,
  versionnable avec le projet).

Backend des commandes : `files::read_project_commands` / `save_project_commands` (`.pilot/commands.json`), `terminal::spawn_terminal_command` (PTY avec `cwd` + commande), frontend `src/js/project-commands.js`.
